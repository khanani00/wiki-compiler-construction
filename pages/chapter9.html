Chapter 9 — Function Calls and the Call Stack

Crossing the boundary between two functions — passing arguments, returning values, and protecting registers across a call.

Opening Problem

In Chapter 6 we translated the body of gcd into flat intermediate code, and in Chapter 8 we fitted its variables into four registers. But both chapters treated a single function body in isolation. The GCD program is not one function — it is main calling gcd:

main(number a, number b) {
  number result := 0;
  result := gcd(a, b);   /* one line — but a whole protocol */
  return result
}

That single line hides four questions the code generator must answer. How does main hand a and b to gcd? Where does gcd find them? How does gcd's answer get back into result? And since both functions want to use the same handful of registers, who makes sure main's values survive while gcd runs?

The answer is a fixed call sequence and a region of memory called the call stack. This chapter builds that protocol for the GCD program.

Learning Objectives

  • Remember what the stack pointer (SP) is and how a stack frame is laid out for a call.
  • Understand the division of labour between the caller and the callee across a function call.
  • Understand the difference between the caller-saves and callee-saves register strategies.
  • Apply the call sequence to translate result := gcd(a, b) into intermediate code.
  • Apply the prologue/epilogue pattern to give gcd an entry and exit that cooperate with its caller.
  • Analyse how the stack changes, slot by slot, as the call to gcd is made and returns.

Connecting to What You Already Know

From Chapter 6 we have the intermediate code for gcd, using v0 = a, v1 = b, v2 = temp, and temporaries t1–t8. From Chapter 8 we know that body fits in four registers. What is still missing is the glue: the code that lets main invoke gcd and recover its result. That glue is what Mogensen calls the call sequence and the function's prologue and epilogue.

Notation used throughout this chapter

SPthe stack pointer — the memory address of the current frame's top slot
SOIsize of an integer, in bytes — the stride between adjacent stack slots
M[addr]the memory cell at addr
nnumber of parameters the called function takes (for gcd, n = 2)
knumber of registers in use that must be preserved
framesizebytes a function reserves for its return address and local variables

The stack grows downward: making room means subtracting from SP (SP := SP - …); releasing room adds back.

9.1 — The Call Stack

When main calls gcd, it cannot simply jump — it must first build a small record on the stack so that gcd knows where its arguments are and where to return to. That record is a stack frame. For a call with n parameters, the frame holds n + 1 slots: one per argument, plus one for the return address.

Frame for the call gcd(a, b)  (n = 2 → 3 slots)

M[SP] return address where gcd jumps back to when it finishes
M[SP + SOI] argument 1 → a also where the return value comes back
M[SP + SOI * 2] argument 2 → b last argument slot

Notice the second line: the return value is delivered in the same slot that held the first argument (M[SP + SOI]). That reuse is deliberate — it means the caller always knows exactly where to look for the answer, regardless of how many arguments were passed.

9.2 — The Call Sequence

The call sequence is the code the caller emits around the jump into the callee. There are two conventions for protecting registers, and they differ only in who saves them:

  • Caller-saves: the calling function stores its own live registers before the call and restores them afterwards. The callee is free to clobber anything.
  • Callee-saves: the called function promises to leave the registers as it found them, saving and restoring them itself. The caller does nothing special.

9.3 — Prologue and Epilogue

The call sequence is only one half of the handshake. The callee — here gcd — needs a matching prologue (code at entry that unpacks the arguments and reserves space for locals) and an epilogue (code at exit that stores the return value and jumps back). The prologue and epilogue must agree with whichever save strategy the caller used.

Source: gcd header & return

gcd(number a, number b) {
  number temp := 0;
  ... body ...
  return a
}

Prologue + epilogue (caller-saves)

LABEL gcd
; -- prologue --
v0 := M[SP + SOI]        ; unpack arg a
v1 := M[SP + SOI * 2]    ; unpack arg b
SP := SP - framesize     ; room for locals (temp = v2)

; ... translated body from Chapter 6 ...

; -- epilogue --
SP := SP + framesize     ; release locals
M[SP + SOI] := v0        ; return value (gcd returns a = v0)
returnaddress := M[SP]   ; fetch saved return address
GOTO returnaddress       ; jump back into main

Because the caller already saved the registers, gcd's prologue is short: it only unpacks parameters and makes room for temp. It never touches R0…Rk.

Source: gcd header & return

gcd(number a, number b) {
  number temp := 0;
  ... body ...
  return a
}

Prologue + epilogue (callee-saves)

LABEL gcd
; -- prologue --
SP := SP - SOI * (k + 1) ; room to save registers
M[SP] := R0              ; save the registers gcd will use
...
M[SP + SOI * k] := Rk
v0 := M[SP + SOI*k + SOI]     ; arg a (now above saved regs)
v1 := M[SP + SOI*k + SOI*2]   ; arg b
SP := SP - framesize          ; room for locals

; ... translated body from Chapter 6 ...

; -- epilogue --
SP := SP + framesize
M[SP + SOI*k + SOI] := v0     ; return value where arg a was
R0 := M[SP]                   ; restore the registers
...
Rk := M[SP + SOI * k]
SP := SP + SOI * (k + 1)      ; release the register-save area
returnaddress := M[SP]
GOTO returnaddress

Here gcd carries the burden: it saves the registers first (so it can use them immediately), which pushes the argument slots up by SOI * k — notice every parameter and return-value offset shifts accordingly.

Watch the Stack During the Call

The clearest way to understand the protocol is to watch memory change. Step through the call to gcd and see how SP moves and what each slot holds.

Step 1 of 6
Before the call

The symmetry that makes it work

Every SP := SP - x in the call sequence is undone by a matching SP := SP + x; every value pushed is later read back from the same offset. The caller and callee never see each other's code — they only agree on the layout of the frame. That contract is what lets gcd be called from main, from itself recursively, or from anywhere else, without either side knowing the other's internals.

Exercises

Remember Exercise 9.1

For the call gcd(a, b), how many stack slots does the frame need, and what does each one hold? Give the offset of each slot relative to SP.

Show answer

Three slots (n + 1 = 3): M[SP] = return address, M[SP + SOI] = argument a (and later the return value), M[SP + SOI * 2] = argument b.

Understand Exercise 9.2

Under the caller-saves strategy, which function emits the M[SP] := R0 … M[SP + SOI*k] := Rk instructions, and when are the matching restores run? Under callee-saves, where do those same instructions move to?

Show hint

Caller-saves: main saves before GOTO gcd and restores at LABEL L0. Callee-saves: the saves/restores move inside gcd's prologue/epilogue — and the argument offsets shift up by SOI * k as a result.

Apply Exercise 9.3

The return value of gcd is read in main with t0 := M[SP + SOI]. Explain why it is read from the first argument's slot rather than from a dedicated return-value slot.

Show hint

gcd's epilogue writes the result with M[SP + SOI] := v0 — the first argument slot. Reusing that slot means the caller needs no extra space and always knows the fixed offset of the answer, independent of n.

Analyse Exercise 9.4

Suppose gcd were made recursive (calling itself on smaller arguments). With the caller-saves strategy, what must be true of the registers and the stack for each nested call to return to the correct place? Which slot keeps the calls from colliding?

Show hint

Each call subtracts SOI * 3 from SP first, so every activation gets its own fresh three-slot frame lower in memory — including its own return-address slot (M[SP]). Because the caller saves its own registers before each call, the live values of the outer activation are preserved on the stack while the inner one runs.

Evaluate Exercise 9.5

The GCD program makes exactly one call (main → gcd), and gcd itself calls nothing. For this specific program, which register strategy produces fewer instructions — caller-saves or callee-saves? Would your answer change if gcd were called from many different places?

Show hint

With one call site, caller-saves emits the save/restore once around that site; callee-saves emits it once inside gcd — roughly even here. Callee-saves wins when a function is called from many sites (the save code lives in one place); caller-saves wins when the caller has few live registers to protect at the moment of the call.

What Comes Next

From intermediate code to a real machine

With functions now callable, the GCD program is a complete, self-contained unit of intermediate code: lexed, parsed, type-checked, translated, register-allocated, and linked across calls. The remaining step is turning this abstract intermediate code — with its unbounded temporaries and symbolic M[SP + …] addresses — into the concrete instruction set of a target processor. The call stack convention built here maps directly onto the hardware stack pointer and the machine's call/return instructions.
