Chapter 6 — Intermediate Code Generation

Translating the syntax tree into flat, executable instructions — one grammar rule at a time.

Opening Problem

You have a fully type-checked syntax tree for the GCD program. The tree has structure — nested expressions, a while loop, assignments. But the machine that will run this program has no concept of trees. It executes a flat sequence of simple instructions: load, store, add, jump.

How do you get from this:

b := a - (a / b * b)    /* nested expression tree */

To this:

t1 := v0            /* load a */
t2 := v0            /* load a again */
t3 := v1            /* load b */
t4 := t2 / t3       /* a / b */
t5 := t4 * v1       /* * b */
t6 := t1 - t5       /* a - (...) */
v1 := t6            /* store result in b */

The answer is syntax-directed translation — a recursive process where every grammar rule has a corresponding translation function. The tree structure guides the translation.

Learning Objectives

  • Remember what intermediate code is and why compilers use it as a stepping stone between source and machine code.
  • Understand how syntax-directed translation works — each grammar rule maps to a trans function.
  • Understand how TransExp and TransStat use newvar, newlabel, vtable, and ftable.
  • Apply TransExp and TransStat by hand to translate expressions and statements from the GCD program.
  • Apply the while-loop translation to produce labelled intermediate code with GOTO jumps.
  • Analyse the generated code to explain why each temporary variable and label was introduced.

Connecting to What You Already Know

In Chapter 5 the type checker walked the syntax tree and verified that every operation made sense. It produced no output code — its job was purely to check. Now in Chapter 6 the same tree is walked again, but this time the goal is to emit instructions.

Critically, the vtable and ftable from Chapter 3 are still in use — but their content has changed. In Chapter 3 the tables stored types. In Chapter 6 they store intermediate-language variable names. The symbol table mechanism is identical; only what it maps names to has changed.

Key point

The syntax tree has no meaning by itself — "guided by ≠ determined by". The compiler engineer creates meaning by designing the appropriate attributions. Each grammar rule gets a trans() function. Every tree node corresponds to a recursive function call. The base case returns empty code; recursive cases append code from children and add their own instruction.

Core Concepts

1. The Intermediate Language

The intermediate language used in this chapter is flat and low-level. Every value must live in a named variable. Every operation produces a result stored in a variable. There are no nested expressions — only sequences of simple instructions.

x := vAssign atom (variable or constant) to x
x := op aUnary operation on atom a
x := a op bBinary operation
LABEL lMark position l as jump target
GOTO lUnconditional jump to label l
IF x relop a THEN l1 ELSE l2Conditional jump
x := CALL f(a1,...,an)Function call
RETURN xReturn value from function

2. Syntax-Directed Translation

Every grammar production has a corresponding translation function. The function for a production walks its children, collects their code, and appends its own instruction(s). This is exactly Gruner's SEQ example from the lecture:

Grammar rule

SEQ ::= COMMAND ; SEQ'
⇆

Translation attribution

trans(SEQ):
  head = trans(COMMAND)
  tail = trans(SEQ')
  code = head ++ tail
  return code

Base case

SEQ ::= ε  /nullable
⇆

Base case translation

trans(SEQ):
  return ""  // empty code

3. TransExp — Translating Expressions

TransExp(Exp, vtable, ftable, place) generates code that evaluates Exp and stores the result in the intermediate variable place. The place is an inherited attribute — the caller decides where the result goes.

TransExp(num, vtable, ftable, place):
  v = getvalue(num)
  return [place := v]

TransExp(id, vtable, ftable, place):
  x = lookup(vtable, getname(id))
  return [place := x]

TransExp(Exp1 binop Exp2, vtable, ftable, place):
  place1 = newvar()
  place2 = newvar()
  code1  = TransExp(Exp1, vtable, ftable, place1)
  code2  = TransExp(Exp2, vtable, ftable, place2)
  op     = transop(binop)
  return code1 ++ code2 ++ [place := place1 op place2]

4. TransStat — Translating Statements

TransStat(Stat, vtable, ftable) generates code for a statement. For control flow (while, if-else) it uses newlabel() to create fresh jump targets and TransCond for conditions.

TransStat(id := Exp, vtable, ftable):
  place = newvar()
  x     = lookup(vtable, getname(id))
  return TransExp(Exp, vtable, ftable, place) ++ [x := place]

TransStat(while Cond do Stat1, vtable, ftable):
  L1 = newlabel()    // loop entry
  L2 = newlabel()    // loop body
  L3 = newlabel()    // loop exit
  condCode = TransCond(Cond, L2, L3, vtable, ftable)
  bodyCode = TransStat(Stat1, vtable, ftable)
  return [LABEL L1] ++ condCode
      ++ [LABEL L2] ++ bodyCode
      ++ [GOTO L1, LABEL L3]

Translating the Function Declaration

The function header gcd(number a, number b) is translated by mapping the parameter names to fresh intermediate variables and creating a function entry in the intermediate language:

  1. newvar() → v0 — bound to parameter a in vtable
  2. newvar() → v1 — bound to parameter b in vtable
  3. Function header emitted: function _gcd(v0, v1)
  4. Local declaration number temp := 0: newvar() → v2, emit v2 := 0

Exercises

Remember Exercise 6.1

What is the purpose of newvar() in intermediate code generation? Why can't we just reuse the source variable names directly?

Show answer

newvar() generates a fresh, previously unused variable name for each intermediate result. We can't reuse source names because: (1) multiple subexpressions need their own storage simultaneously, (2) the intermediate language uses flat variable names with no scoping, so name collisions would occur, and (3) different functions may have variables with the same source name (like a in both main and gcd) that must map to distinct internal names.

Apply Exercise 6.2

Apply TransExp to the expression a - (a / b * b) using the vtable {a→v0, b→v1} and place t7. Show every call to newvar() (assume it returns t1, t2, t3, t4, t5, t6 in sequence) and the code generated at each step.

Show hint

This is a binary subtraction at the top level. Split into left operand a (assign to t1) and right operand (a / b * b). The right operand is itself a multiplication — split again. Keep recursing until you hit variable references and literals (base cases). Build the code from the bottom up.

Apply Exercise 6.3

Apply TransStat to the while loop from GCD: while (b > 0) do { ... }. Show the labels generated, the structure of the emitted code, and explain what happens at runtime when the condition is false on the first iteration.

Show hint

Three labels are needed: L1 (loop entry, target of the back-jump), L2 (body label, jumped to when condition is true), L3 (exit label, jumped to when condition is false). When condition is false on first entry: IF fires → jumps to L3 immediately, skipping the body entirely. GOTO L1 is never reached.

Analyse Exercise 6.4

Count the number of intermediate instructions generated for the single source statement b := a - (a / b * b). Then explain why this is more instructions than necessary and what a later optimisation pass might do to reduce it.

Show hint

Count: 7 instructions (t2:=v0, t3:=v0, t4:=v1, t5:=t3/t4, t6:=t5*v1, t7:=t2-t6, v1:=t7). The obvious redundancy: a is loaded twice (t2 and t3 both get v0) and b could be used directly. Register allocation (Chapter 8) can eliminate the redundant copies by recognising that t2, t3, and v0 hold the same value.

Evaluate Exercise 6.5

Gruner's lecture noted that "guided by ≠ determined by" — the syntax tree guides but does not fully determine the translation. Give a concrete example from the GCD intermediate code where the compiler engineer made a design choice that could have been made differently, and explain the trade-off.

Show hint

One example: the choice to always copy a variable into a fresh temp before using it (e.g., t2 := v0 rather than using v0 directly as the left operand of subtraction). The trade-off is safety vs efficiency — copying prevents aliasing bugs if the expression has side effects, at the cost of extra instructions. The textbook explicitly discusses this choice in Section 6.4.
