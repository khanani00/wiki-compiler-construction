Chapter 8 — Register Allocation

Mapping many variables into a small number of registers — and handling the overflow.

Opening Problem

In Chapter 6, generating intermediate code for the GCD function produced 11 distinct variables: v0, v1, v2, t1 through t8. A real processor might have only 3 or 4 registers. You cannot put 11 variables in 4 registers simultaneously — but you do not need to. Most variables are only needed for a short stretch of the program. The question is: at any given point, which variables actually need to be in a register at the same time?

That question is answered by liveness analysis. Once you know which variables are live simultaneously, you can decide which ones can share a register — and which ones must be spilled to memory.

Learning Objectives

  • Remember the definition of liveness and the four rules that govern it.
  • Understand how gen, kill, in, and out sets are derived from the intermediate code.
  • Apply fixed-point iteration to compute in/out sets for the GCD function.
  • Apply the interference definition to build an interference graph from the liveness results.
  • Understand how graph colouring maps interference nodes to registers, and what spilling means when colouring fails.

8.1 — Liveness

Definition 8.1 (Mogensen)

A variable is live at some point in the program if the value it contains at that point might conceivably be used in future computations. Conversely, it is dead if there is no way its value can be used in the future.

Four rules determine liveness. The first two define where liveness is generated and killed; the last two define how it propagates:

Rule 1

Generate

If an instruction uses a variable, that variable is live at the start of that instruction.

At instruction 9 (t4 := v1), v1 is used — so v1 is live in at instruction 9.

Rule 2

Kill

If a variable is assigned by an instruction (and not also used as an operand), it is dead at the start of that instruction — the old value is about to be overwritten.

At instruction 13 (v1 := t7), v1 is killed — its previous value is irrelevant.

Rule 3

Propagate backward

If a variable is live at the end of an instruction and that instruction does not assign to it, the variable is also live at the start.

Rule 4

Propagate across successors

A variable is live at the end of instruction i if it is live at the start of any immediately succeeding instruction.

8.2 — Liveness Analysis

Liveness analysis formalises the four rules as equations over sets of variables. For each instruction i, we define:

gen[i]

Variables that instruction i reads — liveness is generated here.

kill[i]

Variables that instruction i writes — liveness is killed here.

in[i]

Variables live at the start of instruction i.

in[i] = gen[i] ∪ (out[i] \ kill[i])

out[i]

Variables live at the end of instruction i.

out[i] = ∪ in[j]  for j ∈ succ[i]

These equations are recursive. We solve them by fixed-point iteration: initialise all in[i] and out[i] to ∅, then repeatedly evaluate the equations in reverse instruction order (backwards, because liveness flows backwards — a use of a variable propagates its liveness toward earlier instructions) until no set changes. The result is guaranteed to be reached because sets only grow and are bounded by the finite set of all variables.

Key observations

  • v0 and v1 are live at instruction 1 — these are the input parameters. This is expected: parameters must be live from the start of the function.
  • v2 is not live at instruction 1 — it is declared and initialised at instruction 1, so its old value is irrelevant before that point.
  • All temporaries (t1–t8) have short live ranges. t1 is only live between instructions 5 and 6. t3 and t4 die at instruction 10. This is the key insight — temporaries can share registers with each other and with v0/v1/v2 as long as their live ranges do not overlap at the same point.
  • The back-edge from GOTO L1 (16 → 2) is why v0 and v1 stay live throughout instructions 1–4. The liveness of v0 and v1 at the start of instruction 3 propagates back through instruction 2 and then back-edge to instruction 16, which in turn makes them live out of instruction 15, and so on.

8.3 — Interference

Definition 8.2 (Mogensen)

A variable x interferes with y if x ≠ y and there is an instruction i such that x ∈ kill[i], y ∈ out[i], and instruction i is not of the form x := y.

Two variables can share a register precisely if neither interferes with the other.

Note two subtleties from the definition:

  • After a copy instruction x := y, x and y contain the same value, so they can share a register even if both are live — hence the exclusion of copy instructions from the interference rule.
  • x may interfere with y even if x is not in out[i] (x is assigned a dead value). The assignment still occupies a register at that point and must not overwrite y.

Register sharing opportunities

  • t1 only interferes with v0. It can share a register with v1, v2, or any t other than through v0's neighbours.
  • t7 only interferes with v2. Short live range — assigned at 12, used at 13, dead after.

Minimum registers needed

The maximum clique in this interference graph (a set of mutually interfering variables) has size 5: {t2, t3, t4, v1, v2} all interfere with each other at instruction 9. This means we need at least 5 registers to hold all variables of _gcd without spilling.

8.4 — Register Allocation by Graph Colouring

Each node in the interference graph is a variable. Each colour is a register number. Two nodes connected by an edge must receive different colours (they cannot share a register). The goal is to colour every node using at most N colours, where N is the number of available registers.

This is the graph colouring problem, which is NP-hard in general. In practice, the following heuristic algorithm (Algorithm 8.3, Mogensen) is used:

Algorithm 8.3 — Colouring Heuristic

Simplify

While nodes remain: if any node has strictly fewer than N edges, push it onto a stack (recording its neighbours) and remove it from the graph. If no such node exists, pick any node and do the same. Repeat until the graph is empty.

Select

Pop nodes from the stack one at a time. Assign the node any colour not used by its recorded neighbours (which are all already coloured at this point). If no colour is available: mark the node for spilling.

Why this works even when a node has ≥ N neighbours

A node with N or more edges is not necessarily uncolourable. Some of its neighbours may receive the same colour, leaving a colour available for this node. The "optimistic" approach is to push such nodes anyway and only declare spill failure in the select phase when we actually run out of colours.

Why only 4 registers are actually needed

Despite the maximum clique of size 5, the coloring above assigns at most 4 distinct colours. This is because the 5 mutually interfering variables {t2, t3, t4, v1, v2} are not all live simultaneously with every other variable — the colouring algorithm exploits the global structure of the graph, not just local cliques. The GCD function can be register-allocated with 4 registers with no spilling.

Chapter 9 → Function Calls and the Call Stack

Register allocation in this chapter treats one function body in isolation. Chapter 9 expands to programs with multiple functions calling each other. Function calls introduce new constraints: arguments and return values must be in specific registers, and a called function may overwrite registers that the caller is still using. Handling this requires calling conventions — agreements about which registers a function may destroy and which it must preserve.
