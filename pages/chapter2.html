Chapter 2 — Syntax Analysis

Building a parser that deterministically knows which rule to apply next.

Opening Problem

Here's the while-loop body in the gcd function from the 

temp := b ;
b := a - ( a / b * b ) ;
a := temp

Learning Objectives

By the end of this article you should be able to:

  • Remember which productions in the Reference Grammar are ambiguous or left-recursive as written.
  • Understand why an ambiguous or left-recursive grammar blocks a deterministic top-down parser, and how bottom-up parsing is able to handle a broader class of grammars.
  • Apply the nullable, FIRST, and FOLLOW sets to parsing algorithms.
  • Analyse a constructed LL(1), SLR, or LR table to determine whether a given cell contains a conflict, and trace which grammar property caused it.
  • Evaluate which parsing strategy — LL(1), SLR, or LR — is suitable for a given grammar rule, justifying the choice by what each strategy can and cannot handle.
  • Create an LL(1), SLR, or LR parsing table from FIRST/FOLLOW sets or item sets, and use it to trace the parse of a real program fragment.

Core concepts

Two families of parsers build the same kind of tree from opposite directions:

  • Top-down: starts at the grammar's start symbol and predicts which production to expand next.
  • Bottom-up: starts at the tokens themselves and repeatedly recognises and collapses ("reduces") pieces matching a production's right-hand side.

These are the methods that will be explored below. All three build the same shape of tree for an unambiguous grammar, they just get there differently.

Connecting to What You Already Know

The previous chapter, Lexical Analysis, ended with a finished token stream. That stream is this chapter's input.

You should also already be comfortable with context-free grammars and derivations from your prerequisite coursework. This chapter turns that into something stricter: not just that a grammar can generate a given token sequence, but which one, single, unambiguous tree it corresponds to, and how a parser builds that tree deterministically rather than by guessing.

Ambiguity

A grammar is ambiguous when some input has more than one valid parse tree — two different, equally legal ways of building the same string from the start symbol. LL(1), SLR, and LR are all built to arrive at exactly one tree per input, not to choose between competing ones.

The Reference Grammar avoids this by construction — every alternative in a production like STAT begins with a distinct, unambiguous token, so none of the methods below ever have to resolve a either-or choice. See the conflict check under LL(1) below, and the dangling-else example of what a real conflict would actually look like if the grammar weren't written this way.

Step 5 — LL(1) Conflict Check

A grammar is LL(1) if and only if no cell contains more than one production. Every cell above has at most one entry — this grammar subset is LL(1).

The interesting case: VARS

VARS has two productions: VARS → ε and VARS → VAR , VARS. FIRST of the non-empty production = {number, text}. The nullable production applies only when t ∈ FOLLOW(VARS) = {)}. The sets {number, text} and {)} are disjoint → no conflict.

What a Conflict Looks Like — Dangling Else

If we allowed both:

STAT → if COND then ALGORITHM
STAT → if COND then ALGORITHM else ALGORITHM

Both have FIRST = {if}. The parse table would have two productions in the same cell for STAT under token if — a conflict. The fix is left-factoring:

STAT      → if COND then ALGORITHM ELSE-PART
ELSE-PART → else ALGORITHM
ELSE-PART → ε

Now STAT has one production for if. ELSE-PART chooses else ALGORITHM (Rule 1) or ε when the lookahead is in FOLLOW(ELSE-PART) (Rule 2). No conflict.

SLR

Building an SLR parser uses the exact same technique as building the lexer's DFA in Chapter 1 — small NFAs combined into one, then converted into a deterministic machine via e-closure and subset construction. The only thing that changes is what a "state" represents: instead of a position in a regular expression, a state here is a set of items — a production with a dot marking how far into it the parser has read so far.

Before we start

The full grammar has too many productions to usefully show every NFA, every connection, and every state. So we are selecting a subset of the productions in grammar, built specifically around this fragment from gcd's while-loop body — not the whole language, just enough to parse exactly this: 

temp := b ;
  b := a - ( a / b * b ) ;
  a := temp

Indtroducing Shift and Goto

Every transition out of a state falls into one of two kinds, depending only on what label it's on.

  • A transition on a terminal is a shift: consume that token from the input and move to the next state.
  • A transition on a nonterminal is a goto: used right after a reduction hands back a completed nonterminal, never consumed directly from the input stream.

Step 4 — Reduce, Accept, and Error

Any state containing a complete item — a production with the dot at the very end — adds a reduce action, marked r followed by the production number from the key above, but only for lookahead tokens in FOLLOW of that production's left-hand side. The special case is the augmented start production: once it's complete with lookahead $, that's accept, marked acc. Every other cell in the terminal table, left blank, is an error: no valid continuation exists from that state on that input — a blank cell already means exactly that, no explicit marking needed.
