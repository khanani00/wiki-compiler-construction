Chapter 2 — Syntax Analysis

Building a parser that deterministically knows which rule to apply next.

Opening Problem

Here's a line from gcd that this whole chapter will come back to:

main(number a, number b) {
  number result := 0;
  result := gcd(a, b);
  return result
}

Lexical analysis already turned this into a token stream. During syntax Analysis, that token stream into a tree — and it is done by following a fixed, mechanical procedure rather than by just reading the line the way you naturally would.

Learning Objectives

By the end of this article you should be able to:

  • Remember which productions in the Reference Grammar are ambiguous or left-recursive as written.
  • Understand why an ambiguous or left-recursive grammar blocks a deterministic top-down parser, and how bottom-up parsing is able to handle a broader class of grammars.
  • Apply the nullable, FIRST, and FOLLOW sets to parsing algorithms.
  • Analyse a constructed LL(1) or SLR table to determine whether a given cell contains a conflict, and trace which grammar property caused it.
  • Evaluate which parsing strategy — LL(1) or SLR — is suitable for a given grammar rule, justifying the choice by what each strategy can and cannot handle.
  • Create an LL(1) or SLR parsing table from FIRST/FOLLOW sets or item sets, and use it to trace the parse of a real program fragment.

Core concepts

Two families of parsers build the same kind of tree from opposite directions:

  • Top-down: starts at the grammar's start symbol and predicts which production to expand next.
  • Bottom-up: starts at the tokens themselves and repeatedly recognises and collapses ("reduces") pieces matching a production's right-hand side.

These are the methods that will be explored below. All three build the same shape of tree for an unambiguous grammar, they just get there differently.

Connecting to What You Already Know

The previous chapter, Lexical Analysis, ended with a finished token stream. That stream is this chapter's input. Running the combined DFA from Chapter 1 over number temp := 0 gives exactly four tokens:

  • number: number (keyword)
  • temp: _vname
  • :=: :=
  • 0: _number

Two things carried over directly from the lexer matter for everything below: the parser never sees the characters number, temp, or 0 — only the four token categories above — and it never sees the ; stripped off the end either, since that belongs to whatever statement comes after this one, not to this line itself.

You should also already be comfortable with context-free grammars and derivations from your prerequisite coursework.

Ambiguity

A grammar is ambiguous when some input has more than one valid parse tree. LL(1) and SLR are both built to arrive at exactly one tree per input, not to choose between competing ones. We will not use ambiguous grammar anywhere, for this reason.

Ambiguity is a problem you can't solve in general

It's natural to ask: given some grammar, can't we just check whether it's ambiguous? In general, no. Deciding whether an arbitrary context-free grammar is ambiguous is an undecidable problem — there is no algorithm that takes any context-free grammar as input and correctly answers yes or no, for every possible grammar, in finite time. This is a proven limit, in the same family as the halting problem.

Here is what is possible:

  • Prove a specific grammar ambiguous: exhibit two different trees for one string.
  • Prove a specific grammar unambiguous in particular cases: LL(1) and SLR's conflict checks do this — a clean table is a proof for that one grammar

Neither of those is the same as a general test that works on every grammar you could ever write.

The Reference Grammar avoids ambiguity by construction — every alternative in a production begins with a distinct, unambiguous token, so none of the methods below ever have to resolve a genuine either-or choice. See the conflict check section below for a more detailed explanation of how that works.

Nullable

A nonterminal is nullable if it can derive the empty string — directly, via an ε production, or indirectly, by every symbol in one of its productions being nullable itself. Nullable nonterminals matter because they're the reason a parser sometimes has to make a decision with nothing in front of it to look at: if X is nullable, a predictive parser expecting an X has to decide whether to expand it into something real or skip it entirely, based only on what comes after it.

LL(1) Parsing

There are two ways to do LL(1) parsings:

  • Mentally, by eye, following the grammar top to bottom and picking the production that obviously matches. That works fine by hand on a grammar this small.
  • Mechanically, using a fixed table built from FIRST/FOLLOW sets that a parser consults at every step.

LL(1) works when, for every nonterminal, one token of lookahead is always enough to know which production to expand — exactly what the FIRST/FOLLOW sets above exist to check. When every alternative of every nonterminal starts with a different terminal, the grammar qualifies. The subset above qualifies, once one fix is made to it — covered below:

The left-recursion problem

The Reference Grammar writes statement sequencing as STAT → STAT ; STAT — directly left-recursive. A top-down parser expands the leftmost symbol first, so faced with STAT it would try to expand STAT again, then again, forever, without ever reading a token. This isn't a conflict the table can route around; it's a structural mismatch between the rule and the direction LL(1) parses in.

Left recursion example

The fix doesn't change what the grammar accepts

The GCD code can still be translated from this revised grammar — the language accepted is identical. The issue is specifically that STATS must be right-recursive; the current left-recursive form cannot be parsed top-down. With STATS → STAT STATS' and STATS' → ; STAT STATS' | ε, everything works.

STATS' is the nullable nonterminal from the Nullable section above, and it's exactly this rewrite that introduces it — "no more statements" is what its ε production means.

The LL(1) Table

Built directly from the FIRST and FOLLOW sets above — each cell names the one production that applies for that nonterminal under that lookahead token:

LA(N) \ token number_vname:=_number;$
LA(STATS) {number}#0
LA(STATS') {;}#1 FOLLOW(STATS')#2 (ε)
LA(STAT) {number}#3
LA(VAR) {number}#4
LA(VTYPE) {number}#5
LA(VNAME) {_vname}#6
LA(EXPR) {_number}#7
LA(TERM) {_number}#8
LA(FACTOR) {_number}#9

Tracing number temp := 0 $ through this table top to bottom — expand STATS, expand STAT, expand VAR, expand VTYPE, match number, expand VNAME, match _vname, match :=, expand EXPR, expand TERM, expand FACTOR, match _number, then STATS' under $ reduces to ε — every step uses exactly one production, with no backtracking anywhere.

Conflict Check

A grammar is LL(1) if and only if no cell contains more than one production. Every cell above has at most one entry — this grammar subset is LL(1).

The interesting case: STATS'

STATS' has two productions: STATS' → ; STAT STATS' and STATS' → ε. FIRST of the non-empty production = {;}. The nullable production applies only when t ∈ FOLLOW(STATS') = {$}. The sets {;} and {$} are disjoint → no conflict.

What a Conflict Looks Like — Dangling Else

If we allowed both:

STAT → if COND then ALGORITHM
STAT → if COND then ALGORITHM else ALGORITHM

Both have FIRST = {if}. The parse table would have two productions in the same cell for STAT under token if — a conflict. The fix is left-factoring:

STAT      → if COND then ALGORITHM ELSE-PART
ELSE-PART → else ALGORITHM
ELSE-PART → ε

Now STAT has one production for if. ELSE-PART chooses else ALGORITHM (Rule 1) or ε when the lookahead is in FOLLOW(ELSE-PART) (Rule 2). No conflict.

SLR

Building an SLR parser uses the same technique as building the lexer's DFA in Chapter 1: one small automaton per rule, joined together, then turned into a deterministic machine with subset construction.

The textbook shows the DFA and the parsing table as two separate pictures and leaves you to take it on faith that they're the same thing. They are the same thing — the table below is exactly the DFA above it, just written out row by row. Turning each production into an NFA

Each production becomes a chain of states, one for every position of the dot. The dot marks how much of the production has been read, and each arrow is labelled with the symbol the dot moves over. For STAT → VAR := EXPR that is four states joined by three arrows: VAR, then :=, then EXPR. These states are called items. The subset is small enough to show every production: 19 items in total.

The item with the dot at the far right (a complete item) is where a reduce will come from once we reach the table.

NFA to DFA

This is the same construction as Chapter 1's NFA-to-DFA subset construction, applied to item states instead of regex states. Revisit NFA-to-DFA in Chapter 1 if you need a refresher on how it works.

You should now have a complete DFA with 12 states. See below:

From DFA to Table

Recall FOLLOW sets from above.

These sets belong to this small grammar

In the full grammar an expression can also be followed by ;, }, ), and the operators, so FOLLOW(EXPR) is bigger and the same reduce entries would appear under more columns. The rule for filling them in does not change.

  • An arrow on a terminal becomes a shift (s plus the state number): read that token, move there.
  • An arrow on a nonterminal becomes a goto (g plus the state number): after reducing to that nonterminal, move there.
  • A complete item becomes a reduce (r plus the production number): pop the stack, then move to the state indicated by the goto for that nonterminal.
  • Reduce entries only appear under the tokens in that production's FOLLOW set, because those are the only tokens that can legitimately follow that nonterminal.
  • The augmented production is complete with $ next, so that cell is accept.
  • Everything else left blank is an error — no valid continuation exists

Why this row looks the way it does

The start state; nothing has been read yet. The first item has its dot before STAT, so the ε-closure follows the ε-edges: STAT can start with a VAR, a VAR starts with a VTYPE, and a VTYPE starts with the token number. That is why four items are here, and it is why number is the only shift in this row. The goto columns (STAT, VAR, VTYPE) are blank here for shift purposes, but they are not unused — they are exactly what gets consulted once a reduction further down produces one of those nonterminals.

Table entries in plain words

shift number and go to I4; goto on STAT leads to I1; goto on VAR leads to I2; goto on VTYPE leads to I3.

A VTYPE has been recognised. The dot in VAR → VTYPE • VNAME sits before a nonterminal, so the closure adds VNAME → • _vname. That's why this state both shifts on _vname and has a goto column for VNAME — the shift is for reading the token directly, the goto is for after VNAME gets reduced.

The parser has seen VAR :=.
