Chapter 5 — Type Checking

Teaching the compiler to ask: “Does this even make sense?”

Opening Problem

Your parser accepted this program without complaint. It is syntactically valid. But something is wrong:

main() {
  number x := 5;
  text   y := "hello";
  number z := x + y;   /* adding a number to text — should this work? */
}

The parser's job is structure, not meaning. It sees EXPR + EXPR and passes it through. The type checker is the phase that catches this — before the program ever runs.

Learning Objectives

  • Remember what synthesised and inherited attributes are and how they flow through the AST.
  • Understand how CheckExp recursively type-checks an expression using vtable and ftable.
  • Apply CheckExp by hand to trace the type-checking of a concrete expression step by step.
  • Analyse what happens when a type error is detected and how the checker continues past it.
  • Evaluate the design choice of returning a guessed type after an error rather than stopping.

Connecting to What You Already Know

In Chapter 3 you built a symbol table that maps names to information about what those names are bound to. In that chapter the information stored was the type, scope level, and declaration status of each variable.

In Chapter 5 that same symbol table becomes the environment the type checker runs on. Specifically, two tables are passed through every type-checking function:

vtable

Maps variable names to their declared types (number or text in our grammar).

ftable

Maps function names to their signatures — the list of parameter types and the return type.

These are not new data structures. They are the persistent symbol tables from Chapter 3, populated by crawling the AST, now being used to check types.

Synthesised and Inherited Attributes

Before looking at CheckExp, you need to understand how information flows through the AST during type checking. There are two directions:

if x < 5 then x + 1 else 0
vtable, ftable ↓
x < 5 bool ↑
vtable, ftable ↓
x + 1 number ↑
vtable, ftable ↓
0 number ↑
Result type: number ↑ (synthesised from branches)
type ↑ Synthesised — returned upward    ↓ Inherited — passed downward

Inherited attributes (vtable, ftable) are passed down into each recursive call — every subexpression needs to know the current environment.

Synthesised attributes (the type of each subexpression) are returned up — each call tells its caller what type it computed.

CheckExp — The Type-Checking Function

CheckExp takes an expression node from the AST, the variable environment vtable, and the function environment ftable. It returns the type of the expression, or reports an error and returns a guessed type so that checking can continue.

Below is the full function. Each case is colour-coded — click a case to highlight it and see an explanation.

CheckExp — All Cases

num
  → int

id
  t = lookup(vtable, getname(id))
  if t = unbound
    then error(); return number
    else return t

Exp1 + Exp2
  t1 = CheckExp(Exp1, vtable, ftable)
  t2 = CheckExp(Exp2, vtable, ftable)
  if t1 = number and t2 = number
    then return number
    else error(); return number

Exp1 < Exp2
  t1 = CheckExp(Exp1, vtable, ftable)
  t2 = CheckExp(Exp2, vtable, ftable)
  if t1 = t2
    then return bool
    else error(); return bool

if Exp1 then Exp2 else Exp3
  t1 = CheckExp(Exp1, vtable, ftable)
  t2 = CheckExp(Exp2, vtable, ftable)
  t3 = CheckExp(Exp3, vtable, ftable)
  if t1 = bool and t2 = t3
    then return t2
    else error(); return t2

fname(Exps)
  t = lookup(ftable, getname(fname))
  if t = unbound
    then error(); return number
  else
    (t1,...,tn) → t0 = t
    [t'1,...,t'm] = CheckExps(Exps, vtable, ftable)
    if m = n and t1=t'1, ..., tn=t'n
      then return t0
      else error(); return t0

let id = Exp1 in Exp2
  t1 = CheckExp(Exp1, vtable, ftable)
  vtable' = bind(vtable, getname(id), t1)
  return CheckExp(Exp2, vtable', ftable)

Case Explanation

Click a case in the code to see an explanation of what it does and why.

Number literal

A numeric constant always has type number. No lookup needed — the type is known from the token itself.

Example: 42 → number

Variable reference

Look up the variable name in vtable. If it is found, return its declared type. If not found (unbound), report an error and guess number so checking can continue.

Example: if vtable contains x → number, then x → number.

Watch out: if the variable was never declared, lookup returns unbound — this is the undeclared variable error.

Addition

Recursively check both sides. Both must be number. If either is not, report an error. Either way, the result type is number.

Example: x + 5 where x : number → number.

Watch out: x + y where y : text triggers an error. The checker still returns number as a guess and continues.

Comparison

Both operands must have the same type — the comparison works on any type as long as both sides match. The result is always bool.

Example: x < 5 where x : number → bool.

Note: this differs from addition — comparison does not require number, just that both sides match.

Conditional expression

Three recursive calls. The condition must be bool. Both branches must have the same type. The result type is that shared type.

Example: if x < 5 then x + 1 else 0 — condition is bool, both branches are number → result is number.

Watch out: if the branches have different types, an error is reported and the then-branch type is guessed. This is an arbitrary choice.

Function call

Look up the function name in ftable to get its signature. Check that the number of arguments matches and each argument type matches the declared parameter type. Return the function's return type.

Example: if ftable has add → (number, number) → number, then add(x, 5) where x : number → number.

Watch out: wrong number of arguments or a type mismatch both trigger errors.

Let expression

Check the right-hand side expression to find its type. Extend vtable with the new binding. Use the extended table to check the body. Return the body's type.

Example: let z = x + 1 in z < 10 — z gets type number, body type is bool.

Note: a let-expression cannot itself cause a type error — only its subexpressions can.

Key Takeaway from the Trace

Notice that vtable and ftable are passed unchanged into every recursive call. They are inherited — pushed down the tree. The type that each call returns is synthesised — bubbled back up. The final answer (number) is assembled from the bottom of the tree upward.

Exercises

Remember Exercise 5.1

What is the difference between a synthesised attribute and an inherited attribute? Give one example of each from the type-checking phase.

Show answer

A synthesised attribute is computed from the children of a node and returned upward — the type of an expression is synthesised. An inherited attribute is passed downward from a parent to its children — vtable and ftable are inherited, since every subexpression needs access to the same environment.

Apply Exercise 5.2

Given the vtable {x → number, y → text} and an empty ftable, trace CheckExp on the expression x + y. Write out each recursive call, the value returned, and when the error fires.

Show hint

Start at the Exp1 + Exp2 case. Make two recursive calls — one for x (variable lookup) and one for y (variable lookup). Then check whether both returned types are number.

Apply Exercise 5.3

Using the grammar, write a program with a function double that takes a number and returns a number. Manually construct the ftable entry for double, then trace CheckExp on the call double(x + 1) where x : number.

Show hint

The ftable entry for double should be double → (number) → number. Use the function call case of CheckExp. First look up double in ftable, then call CheckExps on the argument list, then compare argument types against the signature.

Analyse Exercise 5.4

When CheckExp encounters a type error, it reports the error and then guesses a return type (usually number) so that checking can continue. What is the risk of this strategy? Can you construct an expression where the guess causes a spurious error to be reported further up the tree?

Show hint

Try an expression like if (x + y) < 5 then ... where y : text. The + fires an error and guesses number. Then the < case gets number on both sides and passes — no spurious error there. Now try nesting the error inside the condition of an if.

Evaluate Exercise 5.5

The textbook's CheckExp always guesses number after a type error. A better alternative is to return an unknown type and treat it as compatible with anything, so that no further spurious errors propagate. What are the trade-offs of each approach? When would the unknown approach fail to catch a real error?

Show hint

Think about what happens when an unknown type flows into a + expression. The checker treats it as compatible and does not report an error. Now think about a situation where two unknown values are compared and the comparison result is used as the condition of an if — has the error been hidden?
