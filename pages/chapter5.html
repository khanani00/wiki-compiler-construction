Chapter 5 — Type Checking

Teaching the compiler to ask: “Does this even make sense?”

Opening Problem

Your parser accepted this program without complaint. It is syntactically valid. But something is wrong:

main(number a, number b) {
  number result := 0;
  result := gcd(a, b);
  return result
}

gcd(number a, number b) {
  number temp := 0;
  while (b > 0) do {
    temp := b;
    b := a - (a / b * b);   /* what if b is text? parser won't catch it */
    a := temp
  };
  return a
}

The parser's job is structure, not meaning. It sees EXPR BINOP EXPR and passes it through regardless of types. The type checker is the phase that verifies every operation makes sense — before the program ever runs.

Learning Objectives

  • Remember what synthesised and inherited attributes are and how they flow through the AST.
  • Understand how CheckExp recursively type-checks an expression using vtable and ftable.
  • Apply CheckExp by hand to trace the type-checking of a concrete expression from the GCD program step by step.
  • Analyse what happens when a type error is detected and how the checker continues past it.
  • Evaluate the design choice of returning a guessed type after an error rather than stopping.

Connecting to What You Already Know

In Chapter 3 you built a symbol table that maps names to information about what those names are bound to. For the GCD program, that process produced the following tables:

vtable (inside gcd)

a → number
b → number
temp → number

ftable (global)

gcd → (number, number) → number
isZero → (number) → number

These are not new data structures. They are the persistent symbol tables from Chapter 3, populated by crawling the AST, now being used to check types. The type checker inherits them and passes them through every recursive call.

Synthesised and Inherited Attributes

Before looking at CheckExp, you need to understand how information flows through the AST during type checking. There are two directions:

a - (a / b * b)   (from gcd body)
vtable, ftable ↓
a number ↑
vtable, ftable ↓
(a / b * b) number ↑
Result type: number ↑ (synthesised — subtraction of two numbers)
type ↑ Synthesised — returned upward    ↓ Inherited — passed downward

Inherited attributes (vtable, ftable) are passed down into each recursive call — every subexpression needs to know the current environment.

Synthesised attributes (the type of each subexpression) are returned up — each call tells its caller what type it computed.

CheckExp — The Type-Checking Function

CheckExp takes an expression node from the AST, the variable environment vtable, and the function environment ftable. It returns the type of the expression, or reports an error and returns a guessed type so that checking can continue.

Below is the full function. Each case is colour-coded — click a case to highlight it and see an explanation.

CheckExp — All Cases

num
  → number

id
  t = lookup(vtable, getname(id))
  if t = unbound
    then error(); return number
    else return t

Exp1 + Exp2  (or -, *, /)
  t1 = CheckExp(Exp1, vtable, ftable)
  t2 = CheckExp(Exp2, vtable, ftable)
  if t1 = number and t2 = number
    then return number
    else error(); return number

Exp1 < Exp2  (or >, =, <=, >=)
  t1 = CheckExp(Exp1, vtable, ftable)
  t2 = CheckExp(Exp2, vtable, ftable)
  if t1 = t2
    then return bool
    else error(); return bool

if Exp1 then Exp2 else Exp3
  t1 = CheckExp(Exp1, vtable, ftable)
  t2 = CheckExp(Exp2, vtable, ftable)
  t3 = CheckExp(Exp3, vtable, ftable)
  if t1 = bool and t2 = t3
    then return t2
    else error(); return t2

fname(Exps)
  t = lookup(ftable, getname(fname))
  if t = unbound
    then error(); return number
  else
    (t1,...,tn) → t0 = t
    [t'1,...,t'm] = CheckExps(Exps, vtable, ftable)
    if m = n and t1=t'1,...,tn=t'n
      then return t0
      else error(); return t0

let id = Exp1 in Exp2
  t1 = CheckExp(Exp1, vtable, ftable)
  vtable' = bind(vtable, getname(id), t1)
  return CheckExp(Exp2, vtable', ftable)

Case Explanation

Click a case in the code to see an explanation of what it does and why.

Number literal

A numeric constant always has type number. No lookup needed.

In GCD: 0 in number temp := 0 → number

Variable reference

Look up the variable name in vtable. If found, return its declared type. If not found, report an error and guess number.

In GCD: lookup(vtable, "a") → number ✓

Watch out: if b were undeclared, lookup returns unbound — undeclared variable error.

Arithmetic (BINOP)

Both operands must be number. Result is number. This covers +, -, *, / in the referenced grammar.

In GCD: a / b — both number → number ✓

Watch out: a - (a / b * b) requires three nested arithmetic checks, each returning number.

Comparison (RELOP)

Both operands must have the same type. Result is always bool.

In GCD: b > 0 — b : number, 0 : number → bool ✓

In isZero: x = 0 — x : number, 0 : number → bool ✓

Conditional (if-then-else)

Condition must be bool. Both branches must have the same type. Result is that shared type.

In isZero: condition x = 0 is bool ✓, then-branch 1 is number, else-branch 0 is number — match ✓ → result number.

Function call

Look up the function in ftable. Check argument count and types. Return the declared return type.

In main: gcd(a, b) — ftable has gcd → (number, number) → number. a : number, b : number — match ✓ → returns number.

Let expression

Check the RHS, extend vtable, check the body with the extended table.

Not directly used in GCD (declarations use assignment syntax), but the same pattern applies: once a variable is bound, its type flows into all subsequent uses via the extended vtable.

Phase 1 — CheckProgram

Key Takeaway from the Trace

The expression a - (a / b * b) involves five variable lookups and three arithmetic operations, all nested. Every single recursive call receives the same vtable and ftable — inherited unchanged from above. Each call returns number upward — synthesised from below. The final result is number, which matches the declared type of b, so the assignment is valid.

Type-Checking the Full gcd Function

Once the expressions are checked, CheckFun verifies the whole function. For gcd:

  1. GetTypeId extracts the declared return type: number.
  2. CheckTypeIds builds the vtable: {a → number, b → number} and confirms no duplicate parameter names.
  3. bind("temp", number) is added when the local declaration is processed.
  4. CheckExp is called on the body — the while loop, its condition, and all statements inside.
  5. The return expression a is type-checked: lookup(vtable, "a") → number.
  6. Declared return type (number) matches body type (number) → no error.

Known Error in Mogensen (2nd ed.) — Fig. 5.3 and Fig. 5.4

The textbook contains two logically inverted conditions.

As printed, CheckFun fires an error when the declared return type matches the body — the exact case where no error should occur. Implement the corrected versions above.

Known Errors in Mogensen (2nd ed.) — Fig. 5.3 and Fig. 5.4

The textbook contains two logically inverted conditions that were lost in typesetting. Implementing the code as printed will produce a type checker that rejects correct programs and silently accepts incorrect ones.

FigureFunctionAs printed (wrong)Correct version

In both cases the error should fire when the types do not match (≠), not when they do. The condition was almost certainly inverted during typesetting — the = sign should be ≠.

What is the difference between a synthesised attribute and an inherited attribute? Give one example of each from the GCD type-checking trace above.

Show answer

A synthesised attribute is computed from the children and returned upward — e.g. the type number returned by CheckExp(a, ...). An inherited attribute is passed downward — e.g. the vtable containing {a, b, temp} passed into every recursive call inside gcd.

Evaluate Exercise 5.5

The textbook's CheckExp always guesses number after a type error. A better alternative is to return an unknown type compatible with anything. What are the trade-offs? When would unknown fail to catch a real error in the GCD program specifically?

Show hint

Think about what happens if unknown flows into the condition b > 0. The comparison case checks t1 = t2 — if one is unknown and the other is number, does it pass? If you treat unknown as matching anything, the error is hidden. Is hiding it acceptable here?

The type information gathered here does not disappear. In Chapter 6, the code generator uses type annotations from this phase to decide which machine instructions to emit. For the GCD program, knowing that a, b, and temp are all number tells the code generator to emit integer arithmetic instructions throughout — no runtime type checks needed.
