Chapter 3 — Scopes and Symbol Tables

“Scope defines the boundaries; context dictates the meaning.”

Opening Problem

Your parser has just produced a syntax tree for the program below. Both x variables are valid identifiers — but are they the same variable? How does the compiler tell them apart?

main() {
  number x := 5;
  {
    number x := 10;   /* inner x — different variable */
    x := x + 1;
  }
  x := x + 1;        /* outer x restored */
}

The syntax tree knows the structure of this program. It does not know what x means at each point. That is the job of the symbol table.

Learning Objectives

By the end of this article you should be able to:

  • Remember what a symbol table is and what operations it supports.
  • Understand how lexical (static) scoping works and how scope is represented in a syntax tree.
  • Understand the difference between persistent and imperative symbol table implementations.
  • Apply tree-crawling to populate a symbol table from a given program.
  • Analyse a code block, identify scopes, and construct the corresponding symbol table by hand.
  • Create a symbol table for a program written in the unified COS341 grammar.

Connecting to What You Already Know

In Chapter 2 you built a parser that takes a stream of tokens and produces an abstract syntax tree (AST). The AST captures the grammatical structure of the program — which expressions nest inside which statements, how conditions relate to branches, and so on.

But the AST is context-free. It was built using a context-free grammar, which means it carries no information about what names mean. Two uses of the name x look identical in the tree even if they refer to completely different variables.

Chapter 3 is where semantic analysis begins. The compiler now needs to understand context — specifically, which declaration each use of a name refers to. This is called binding, and the data structure that records it is the symbol table.

Key Connection

You will use the symbol table you build here again in Chapter 5 (Type Checking), where it becomes the environment passed to the type checker. Every vtable and ftable you see in Chapter 5 is an instance of what is described in this chapter.

Core Concepts

1. Binding and Scope

A declaration introduces a name and associates it with an item (a variable, a function, a type). This association is called a binding. A use of a name is a reference to the item it is bound to.

The scope of a declaration is the region of the program where that binding is visible. In the unified grammar used across these articles, a scope corresponds to an ALGORITHM block — the region enclosed by { STAT }.

Scoping based on the structure of the syntax tree is called lexical (static) binding. The rule is: a use of a name refers to the closest enclosing declaration of that name — that is, the declaration in the smallest subtree that contains both the declaration and the use.

2. The Symbol Table

A symbol table (also called an environment) is a mapping from names to information about the items those names are bound to. For variables, that information typically includes:

  • Name — the identifier as it appears in the source
  • Type — number or text in our grammar
  • Scope level — how deeply nested the declaration is
  • Declared — whether the name has been declared before use

The symbol table must support five operations:

OperationWhat it does
emptyCreates a new, empty symbol table with no bindings.
bind(name, info)Adds a binding. If the name already exists, the new binding takes precedence (inner scope shadows outer).
lookup(name)Returns the information bound to name, or unbound if not found.
enter()Opens a new scope — saves the current state so it can be restored later.
exit()Closes the current scope — restores the symbol table to the state it was in before enter().

3. Populating the Symbol Table: Tree Crawling

The symbol table is populated by crawling the syntax tree — visiting every node and recording declarations as they are encountered. The traversal can use either Depth-First Search (DFS) or Breadth-First Search (BFS), but DFS is natural here because scopes are nested and nesting maps directly to recursive tree descent.

General Pseudocode

table = empty()

populate(node, table):
  if node is a declaration:
    bind(table, node.name, {type: node.type, scope: currentScope})
  if node opens a new scope:
    enter()
    for each child of node:
      populate(child, table)
    exit()
  else:
    for each child of node:
      populate(child, table)

return table

4. Implementations

There are two main families of implementation. The key difference is in how scopes are managed.

Persistent (Functional)

The old symbol table is never destroyed. When you bind a new entry or enter a scope, a new version of the table is created that shares most of its structure with the old one. When you exit a scope, you simply go back to using the old reference — it was never touched.

Natural in functional languages (SML, Haskell). Required when closures need to capture an environment that outlives its scope.

Underlying structure: Association list (linked list of name/value pairs)

Imperative (Stack-based)

One copy of the symbol table exists. New bindings are pushed on a stack. When you enter a scope, a marker is pushed. When you exit, everything down to the marker is popped, restoring the table to its previous state.

Natural in imperative languages (C, Java). Efficient for simple scoping where closures are not needed.

Underlying structure: Stack with scope markers

5. Efficiency: Hashing

Both simple implementations use linear search for lookup — the table is scanned from top to bottom until a matching name is found. For small programs this is fine, but real programs use libraries that define hundreds of names, making linear search slow.

The standard solution is a hash table: each name is hashed to an integer index into an array. Each slot in the array holds a short list of entries that share the same hash. With a large enough array, these lists stay very short and lookup is effectively constant time.

For imperative implementations, a single auxiliary stack records all updates so that scope exit can undo them in time proportional to the number of bindings added in that scope, without rescanning the whole table.

6. Separate vs Shared Name Spaces

Some languages (Pascal) allow a variable and a function to share the same name because the context of use makes it clear which is meant. These have separate name spaces. Other languages (C, SML) have a shared name space where a local variable can shadow a function of the same name.

Separate name spaces are implemented with one symbol table per name space. A shared name space uses one table for everything, sometimes with a prefix or tag added to each name to distinguish its kind.

Source Program

  number y := 10;
  {

Trace: What Happens During Tree Crawl

Walking the AST depth-first, left to right, the following events occur:

  1. enter() — program starts, scope level 0 begins.
  2. bind("x", {type: number, scope: 0}) — outer x declared.
  3. bind("y", {type: number, scope: 0}) — y declared.
  4. enter() — inner block { } begins, scope level 1.
  5. bind("x", {type: number, scope: 1}) — inner x declared. This shadows the outer x; lookup("x") now returns scope 1.
  6. lookup("y") — y not in scope 1, found in scope 0. Resolves correctly.
  7. exit() — inner block ends. Inner x is removed. Outer x is restored.
  8. lookup("x") — now resolves to scope 0 again.
  9. exit() — program ends.

What Comes Next

Chapter 5 → Type Checking

The symbol table you built here becomes the environment that the type checker operates on. In Chapter 5, you will see two symbol tables passed through every function: vtable, which maps variable names to their types, and ftable, which maps function names to their signatures. These are exactly the persistent symbol tables described in this chapter — implemented using the bind, lookup, and empty operations you have just learned.

Without the symbol table, the type checker has no way to know what type x is when it appears in an expression. The work done in this chapter is what makes type checking possible.
