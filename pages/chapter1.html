Chapter 1 — Lexical Analysis

“Scope defines the boundaries; context dictates the meaning.”

Opening Problem

Here is a fragment from a program 

x := 5 ; y := x + 1

To you, these two statements are apparent to you: assign 5 to x, then assign x + 1 to y separated by a semicolon.

To a compiler, this is source file with a stream of characters.

Before the parser can build any structure, something has to scan these raw characters and group them into tokens: identifiers, operators, number, variable etc.

This something is the lexer

Why do we need a lexer?

A compiler's job, broadly, is to turn source code into something a machine can run. That happens in stages — lexical analysis, syntax analysis, type checking, code generation — and lexical analysis is the first one, because every later stage needs to work with meaningful tokens (identifiers, numbers, operators), not raw characters.

A lexer groups characters into tokens, discard what doesn't matter (whitespace, comments), and hands the parser a clean, categorised stream to work with.

Learning Objectives

By the end of this article you should be able to:

  • Remember the token types used in the Reference Grammar
  • Understand why regular expressions alone are not directly executable, and why NFAs and DFAs exist as a construction path between a regex and a working program.
  • Understand the difference between an NFA and a DFA, and why lexers are built on DFAs specifically.
  • Apply subset construction to convert a small NFA into a DFA.
  • Understand how longest-match and priority rules resolve token boundaries, by following a full scan trace step by step.
  • Understand how a combined DFA and the scan() algorithm together implement a working lexer.

Core Concepts

Two thing sneeds to be made clear before any construction can happen: What the lexer needs to recognize (token types/categories) and how each one is described (using regular expression definitions). Everything else in the chapter builds on these two things.

Regular Expression

A regular expression is a compact pattern language for describing a set of strings — not a specific string. Each token type in our grammar gets exactly one regular expression, and anything that matches it is a valid instance of that token.

Token types in the Reference Grammar, with the regular expression that defines each:

Type/CategoryExamplesRegular Expression
Keyword/ _text reserved words: main, if, while, return matches the literal word, e.g. "if"
_vname (identifier) x, y, total code>[a-zA-Z][a-zA-Z0-9]*
_number (numeral literal) 5, 123 [0-9][0-9]*
:= assignment ":="
+ addition operator "+"
; statement separator ";"

These are the six token types this chapter's worked examples use. The same style extends to the rest of the grammar's terminals when needed.

Pipeline

The problem this whole chapter tries to resolve: regualr expression tells you what a token looks like, but it is not a program, hence cannot be executed by a computer. Getting from "description of a pattern" to "working code that recognizes that pattern" takes a couple of steps. This is that path:

1. Regex

Human readable specification describing a pattern.

2. NFA

Built from a regualar expression (specification), one construction rule per operator. The problem with NFA is that it can be in several states at once, due to epsilon-transitions, this not something a simple loop can track directly.

3. Subset construction (NFA to DFA)

Solves previous problem bytracking sets of NFA as single DFA states. The result has no epsilon-transitions and exactly one next state per input character.

4. Minimisation

The DFA that subset construction produces often has more states than necessary. This step merges any states that behave identically going forward, and removes dead states (ones that can never lead to acceptance).

5. Combined DFA

So far this covers one token type. A real lexer needs to recognize all token types from a single scan, so this step merges every pattern's automaton into one, with each accepting state tagged with which token type it matches.

rules

longest match: always consume the longest valid prefix, not the first thing that happens to match.

priority: when two token types could both match the same longest string (a keyword like number also matches the _vname pattern), a fixed order decides the winner - usually keywords (reserved words like if, return etc get first preference)
