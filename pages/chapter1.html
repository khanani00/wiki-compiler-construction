Chapter 1 — Lexical Analysis

“The pattern defines the boundary; longest match decides where one token ends and the next begins.”

Opening Problem

Here is a fragment from a program:

x := 5 ; y := x + 1

To you, these two statements are immediately clear: assign 5 to x, then assign x + 1 to y, separated by a semicolon.

To a compiler, this is a source file — a stream of characters.

Before the parser can build any structure, something has to scan these raw characters and group them into tokens: identifiers, operators, numbers, keywords and so on.

This something is the lexer.

Why do we need a lexer?

A compiler's job, broadly, is to turn source code into something a machine can run. That happens in stages — lexical analysis, syntax analysis, type checking, code generation — and lexical analysis is the first one, because every later stage needs to work with meaningful tokens (identifiers, numbers, operators), not raw characters.

A lexer groups characters into tokens, discards what doesn't matter (whitespace, comments), and hands the parser a clean, categorised stream to work with.

Learning Objectives

By the end of this article you should be able to:

  • Remember the token types used in the Reference Grammar
  • Understand why regular expressions alone are not directly executable, and why NFAs and DFAs exist as a construction path between a regex and a working program.
  • Understand the difference between an NFA and a DFA, and why lexers are built on DFAs specifically.
  • Apply subset construction to convert a small NFA into a DFA.
  • Understand how longest-match and priority rules resolve token boundaries, by following a full scan trace step by step.
  • Understand how a combined DFA and the scan() algorithm together implement a working lexer.

Connecting to What You Already Know

You should already be comfortable with regular expressions or pattern matching before this chapter. Everything here turns that familiar idea — a compact description of a pattern — into a program that scans character by character.

Core Concepts

Two things need to be made clear before any construction can happen: what the lexer needs to recognise (token types), and how each one is described (a regular expression per type). Everything else in this chapter builds on these two things.

Rules

Longest match: always consume the longest valid prefix, not the first thing that happens to match.

Priority: when two token types could both match the same longest string (a keyword like number also matches the identifier pattern), a fixed order decides the winner — usually keywords (reserved words like if, return, etc.) get first preference.

Error handling: if no transition exists at all from the current state and no accepting state has been passed through, the lexer cannot form a valid token from the characters read so far — this is reported as a lexical error at that position, rather than silently skipped or guessed at.

Creating the DFA

Turning a pattern into something a lexer can actually run takes four stages: regex to NFA, NFA to DFA, combining every token type's DFA into one, then minimising the result. Each stage below is broken out per token type — the diagram areas are left blank intentionally for hand-drawn illustrations.

Step 1 — Regex to NFA

The NFA represents all valid patterns that can belong to that token group. An NFA can contain epsilon (ε) transitions, which allow the automaton to move from one state to another without reading an input character. An NFA may also allow more than one possible transition from a state.

The final accepting states represent valid matches for the token.

The keyword NFA was constructed by following the characters of each keyword in sequence. Separate paths were created for keywords such as return, main, if, else, and while. After the final character of a keyword is read, an epsilon (ε) transition leads to a common accepting state.

The identifier NFA accepts names consisting of letters followed by zero or more letters or digits.

The first character must be a letter, represented by [a-zA-Z]. After this, the identifier may contain letters or digits, represented by [a-zA-Z0-9].

The number NFA accepts positive whole numbers and decimal numbers according to the chosen lexical rules.

The automaton separates numbers beginning with 0 from numbers beginning with [1-9]. This allows the grammar to control which number formats are considered valid.

For multi-digit numbers, transitions labelled [0-9] allow the automaton to continue reading digits.

A decimal point (.) moves the automaton into the decimal part of the number. The remaining transitions ensure that the digits after the decimal point follow the required number rules.

The NFA follows a transition on : and then a transition on = to reach the accepting state.

The relational operator NFA begins by branching according to the first character read: <, >, or =. These operators can form valid relational operators on their own

After reading < or >, the NFA may also read an additional = to form <= or >=.

Epsilon transitions connect the completed operator states to a common accepting state.

The operator NFA accepts the arithmetic operators +, -, *, and /.

Each operator is represented by a transition from the start state. After reading a valid operator, an epsilon transition leads to a common accepting state. This allows all arithmetic operators to be represented within one NFA.

The symbol NFA accepts punctuation symbols used by the language, including (, ), {, }, ;, and ,.

Each symbol is represented by its own transition from the start state. Epsilon transitions are then used to connect the completed symbol paths to a common accepting state.

Step 2 — NFA to DFA

The NFA is converted into a DFA using epsilon-closure and subset construction.

The epsilon-closure of a state is the set containing that state and all other states that can be reached using only epsilon (ε) transitions. An epsilon-closure can be understood as asking: "Where can I reach without reading another character?"

A DFA contains no epsilon transitions. For each input symbol, the DFA has only one possible transition from a particular state.

The DFA was obtained by removing the epsilon transitions through subset construction. The extra accepting state reached through epsilon transitions is absorbed into the corresponding DFA states. Therefore, the state reached after reading the final letter of each keyword becomes an accepting state directly.

The resulting DFA has no epsilon transitions and follows one deterministic path for each keyword.

During conversion to a DFA, the epsilon transitions are removed.

After reading the first letter, the DFA enters an accepting state because a single letter is already a valid identifier.

The DFA remains in the same accepting state while additional letters or digits are read. This creates a simple loop for [a-zA-Z0-9].

For the Number NFA, letters are used to name the DFA states instead of numbers. This makes it easier to distinguish the DFA states from the numbered states of the original NFA.

The DFA state names A to G therefore represent sets of NFA states.

Nr Current State ε-Closure 0 [1-9] .
A {0} {0} B C -
B {1} {1} - - D
C {2} {2} E E D
D {4} {4} F G -
E {3} {2,3,7} E E D
F {5} {4,5} F G -
G {6} {6,7,4} F G -

Each letter represents a DFA state created during subset construction. A transition marked - means that no valid transition exists for that input.

Since the automaton has no epsilon transitions and only one valid path for the token, the conversion from NFA to DFA is straightforward.

Each row represents a DFA state created from one or more NFA states. The initial DFA state is numbered 0.

Nr Current State ε-Closure < > =
0 {0} {0} 1 3 2
1 {1} {1,4} - - 2
2 {2} {2,4} - - -
3 {3} {3,4} - - 2

States whose ε-closure contains the accepting NFA state 4 are accepting states in the DFA.

During conversion to a DFA, the epsilon transitions are removed.

The states reached after reading +, -, *, or / become accepting states directly.

The DFA is obtained by removing the epsilon transitions and incorporating the accepting state into the states reached after reading each valid symbol. Each valid punctuation symbol therefore leads directly to an accepting DFA state.

Step 3 — Minimise the DFAs

Every DFA above except one is already minimal: Identifier (2 states), Assign (3 states), Operator (3 states, after merging the shared paths), and every Symbol (2 states each) all came out of subset construction with no equivalent states left to merge. Number is the one exception — its two candidate states after subset construction turn out to be equivalent and collapse into one, the same way Identifier's did. That's the only minimisation actually worked through below.

Step 4 — Combine the minDFAs

With every individual DFA now confirmed minimal, combining them is just attaching each one's start state to a single shared S0 — check the token table above and none of the seven categories share a first character, so no branch competes with another for the same transition.

Step 5 — Completed DFA, Ready for Lexing

With every token type minimised and combined into one machine, the lexer has everything it needs: a single automaton that recognises any token in the language, one character at a time.

Key Takeaway from the Trace

Every step above follows the same two rules: consume characters while a transition exists, and only accept once none does (longest match); when a character could complete more than one token type, whichever pattern is listed first wins (priority). This trace is itself pseudocode for the scanner: start at S0, follow a transition if one exists, remember the last accepting state you passed through, emit a token and reset to S0 once none exists.

Closing

This chapter took one small idea — a regular expression describing a pattern — and carried it all the way to a working scanner: regex to NFA, NFA to DFA, DFA to minimised DFA, and finally every token's minimised DFA combined into one. The trace above showed that combined machine actually reading a fragment of source code, one character at a time, emitting a token every time longest-match and priority say it should.

Key Connection

The token stream produced above is exactly what Chapter 2's parser takes as input. Every token category defined in this chapter becomes a terminal symbol in the grammar used for parsing.

Exercises

Apply Exercise 1.1

Given the regex [ab]*c, construct the NFA, then apply subset construction to get the DFA.

Show answer

Using Thompson's construction: build an NFA for a, one for b, combine them with a union (a|b), apply the Kleene-star construction to get (a|b)*, then concatenate an NFA for c onto the end. The result has a single accepting state, reached only after zero or more a/b characters followed by exactly one c.

Applying subset construction: the start state's $\epsilon$-closure includes every state reachable before consuming input. On each a or b, the closure stays within the "looping" part of the machine — so a single DFA state can represent this entire loop, since a and b both lead back to the same set of NFA states. On c, that DFA state transitions to a new, accepting DFA state. Any further a, b, or c from the accepting state has no valid continuation of this pattern and goes to a dead state.

Analyse Exercise 1.2

A DFA has two states that both transition identically on every input symbol and lead only to rejection. Explain why these can be merged during minimisation, and what would go wrong if they were not merged in a large lexer with hundreds of token types.

Show answer

Two states are equivalent for minimisation if, for every possible remaining input, they either both lead to acceptance or both never do — from the scanner's point of view, they behave identically no matter what comes next, so keeping them separate adds no distinguishing power. Since both states here always lead only to rejection regardless of input, they meet exactly that condition and can be collapsed into one dead state.

If they were not merged, every additional token type introduces its own redundant dead states rather than sharing the DFA's existing ones. In a lexer with hundreds of token types, this multiplies the number of states and the size of the transition table without changing which strings are recognised — it costs memory and lookup time for no benefit.

Create Exercise 1.3

Following the same four-step pipeline used above, construct the minimised DFA for the Number token ([0-9][0-9]*) and for the semicolon symbol. Compare their size to the identifier's DFA — why is one so much smaller than the others?

Show answer

Number follows the exact same shape as identifier: one non-accepting start state, one accepting state reachable by consuming a character from the relevant class, and a self-loop on that accepting state for every character after the first. Only the character class changes — digits instead of letters-then-alphanumerics.

The semicolon is the simplest possible case: a single-character token. Its minimised DFA has exactly two states — a start state and an accepting state reached on ;, with no loop, since nothing can extend a valid semicolon token further. That's why it's smaller than the others: there's nothing to repeat.
